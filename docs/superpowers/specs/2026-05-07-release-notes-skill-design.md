# release-notes スキル 設計

## 概要

GitHub Releases の body に、コミットログから生成したリリースノート（`## 新機能` / `## バグ修正` / `## その他の変更`）を埋めるためのリポジトリスキル。

- **配置**: `bms-elsa/.claude/skills/release-notes/SKILL.md`（リポジトリ管理）
- **呼び出し**:
  - 引数なし → 最新 GitHub Release を対象
  - 引数あり（`v0.11.2` または `0.11.2`）→ 指定リリースを対象
- **出力先**: 対象リリースの body（`gh release edit --notes-file`）

### スコープ外（YAGNI）

- ローカル `.md` ファイルへのリリースノート保存（既存の `docs/release-notes/` は本スキル実装後に削除予定）
- ドラフトリリース／タグの新規作成（既存リリースの body 更新のみ）
- 多言語対応（日本語のみ）

## 入力処理とバージョン解決

### バージョン正規化

- 引数が `0.11.2` のように `v` なし → `v0.11.2` に正規化
- 引数なし → `gh release list --limit 1 --json tagName --jq '.[0].tagName'` で最新リリースタグを取得

### 対象リリース存在確認

- `gh release view <tag>` を実行
- リリースが存在しない場合はエラーで停止

### 前バージョン解決

GitHub Releases の `publishedAt` 順で1つ前のリリースを「前バージョン」とする。

```bash
gh release list --limit 100 --json tagName,publishedAt \
  --jq 'sort_by(.publishedAt)'
```

- 上記の配列で対象タグの直前のエントリを採用
- 対象が最古リリースの場合: 前バージョン = リポジトリ最初のコミット
  - `git rev-list --max-parents=0 HEAD | head -1`

> リリース順序が時系列で入れ替わる運用は想定しない（SemVer 順 == published 順）。

## 差分取得と分類

### コミット取得

```bash
git log <prev>..<target> --no-merges \
  --pretty=format:'%H%x09%s%x09%b%x1e'
```

- `<target>` は対象タグ
- `<prev>` は前バージョンのタグ、または最古リリースのときは最初のコミットハッシュ
- merge コミットは除外
- レコード区切りは `\x1e`、フィールド区切りは `\t`（コミット本文の改行を保持するため）

### LLM による分類

取得したコミット一覧を LLM が読み、次の4カテゴリに振り分ける。

| 分類 | 内容 |
|---|---|
| 新機能 | ユーザーから見える新しい機能の追加 |
| バグ修正 | ユーザーから見える不具合の修正 |
| その他の変更 | ユーザーから見える挙動変更・機能削除・破壊的変更など |
| 除外 | ドキュメント・内部リファクタ・テスト・CI・依存更新など、ユーザーに見えない変更 |

#### 判定の指針（SKILL.md に明記する）

- prefix（`feat:`/`fix:`/`refactor:` など）はヒントとして参照、最終判断はメッセージ全文の内容で行う
- 迷った場合は「ユーザー視点で挙動が変わるか」を基準にする
- 全コミットが「除外」になった場合は、その旨を出力して停止（空のリリースノートで上書きしない）

## 文章生成と出力フォーマット

### 文章スタイル規約

過去リリースノート（`docs/release-notes/v0.11.0.md` など）の文体に倣う。

- 各項目は完結した文（体言止め禁止、「〜した」「〜を追加」「〜を修正」のような述語で締める）
- 背景・対象・挙動を含めて1〜2文で説明
- コードシンボルは バッククォートで囲む（例: `config.json`）
- 同じ機能領域に関する複数コミットは1項目にまとめる（バグ修正の積み重ねなど）

### セクション構成

```markdown
## 新機能
- ...

## バグ修正
- ...

## その他の変更
- ...
```

- 順序: `## 新機能` → `## バグ修正` → `## その他の変更`
- 該当項目がないセクションは出力しない

### フォーマット例

```markdown
## 新機能
- 詳細画面の各カード UI を最小化可能にした。タイトル左の chevron ボタンで展開／最小化を切り替え、状態を `config.json` に保存する。

## バグ修正
- モーダル内コンテキストメニューでクリック／ホバーが効かない問題を修正。

## その他の変更
- 難易度表切替時に Level フィルタを自動でクリアするよう挙動を変更。
```

## 上書き確認とリリース更新

### 既存 body チェック

```bash
gh release view <tag> --json body --jq .body
```

- 空文字列 → 無確認で進む
- 何か入っている → ユーザーに以下を提示してプロンプト：
  - 既存 body の内容
  - 生成した新しい body
  - 「上書きしますか？」と問い、明示的な承認（「はい」「ok」など）を待つ
  - 拒否されたら停止

### リリース更新

承認後（または既存 body が空の場合）:

1. 生成テキストを一時ファイルに書き出し（`Write` ツール）
2. `gh release edit <tag> --notes-file <tmp>` で body を更新
3. `gh release view <tag> --json url --jq .url` で URL を取得し、ユーザーに通知

> `--notes-file` を使うのは、長文・改行・特殊文字を安全にシェルへ渡すため。

### エラーハンドリング

| 事象 | 挙動 |
|---|---|
| `gh` 未認証 | 認証を促すメッセージで停止 |
| 対象タグなし | エラーメッセージで停止 |
| 対象範囲にユーザー向けコミット 0 件 | 「除外対象のみ」と通知して停止（空更新しない） |
| `/tmp` への書き込みがブロック | `save-temp-file` スキルへ誘導 |

## SKILL.md 構造

### frontmatter

```yaml
---
name: release-notes
description: |
  GitHub Releases の body にリリースノートを生成・更新する。
  「リリースノート作成して」「v0.11.2 のリリースノートを作って」
  「最新リリースのノートを更新」などの指示があった場合に使用。
model: claude-sonnet-4-6
allowed-tools:
  - Bash
  - Write
---
```

> 軽量かつ重要性の低い処理のため、利用モデルを Sonnet に固定する。

### 本文セクション

1. 概要（目的・引数仕様）
2. 実行手順（バージョン正規化 → 前バージョン解決 → コミット取得 → 分類 → 文章生成 → 上書き確認 → リリース更新）
3. 分類ルール（新機能 / バグ修正 / その他の変更 / 除外、判定指針）
4. 文章スタイル規約（過去ノートに倣う、述語で締める等）
5. 出力フォーマット（セクション順序、空セクション省略、見出しレベル）
6. エラーハンドリング（gh 未認証・タグなし・該当コミット 0 件）

### 利用ツール

- `Bash`: `gh` / `git` コマンド実行、`gh release edit --notes-file` でリリース更新
- `Write`: 一時ファイル書き出し（`/tmp/` がブロックされた場合は `save-temp-file` スキルへ誘導）

## 後始末（スキル本体外）

- スキル動作確認後、`docs/release-notes/` ディレクトリは削除予定（リポジトリ管理対象から外す）
- マニュアル（`docs/manual.md`）には影響なし
